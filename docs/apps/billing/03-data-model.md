# Data model

The data model stores the billing state that is mirrored from Stripe:
tenants, the catalog, customers, subscriptions and usage events. It is
defined with SQLAlchemy 2 (async, `Mapped` annotations) and versioned with
Alembic.

## Models

All identifiers are UUID strings generated by the application. `created_at`
and `updated_at` default to `now()` on the database side.

```text
SaasApp 1--* BillingProduct 1--* BillingPrice
   |
   1--* Customer 1--* Subscription *--1 BillingPrice (optional)
                           |
                           1--* UsageEvent
```

| Model | Table | Purpose |
|-------|-------|---------|
| `SaasApp` | `saas_apps` | A tenant: unique `slug`, optional webhook URL and secret, JSON `branding`, JSON `checkout_url_allowlist`, `is_active` |
| `BillingProduct` | `billing_products` | A product (plan) of a tenant, mapped to `stripe_product_id`; the plan `slug` is unique per tenant, so `free` or `pro` can exist in every tenant; JSON `extra_data` (features, limits) |
| `BillingPrice` | `billing_prices` | A price of a product: `currency`, `unit_amount` (cents, null for metered or custom), `billing_type`, recurring interval, `usage_type` |
| `Customer` | `customers` | A customer of a tenant, identified by the tenant's `external_id` and by `stripe_customer_id`; soft deleted through `deleted_at` |
| `Subscription` | `subscriptions` | A Stripe subscription with its `status`, billing period and `cancel_at_period_end` |
| `UsageEvent` | `usage_events` | A metered usage record waiting to be reported to Stripe; it carries the `saas_app_id` of its owner and an optional `idempotency_key`, unique per tenant |

Enumerations (stored with their lowercase value):

| Enum | Values |
|------|--------|
| `BillingType` | `one_time`, `recurring` (default) |
| `UsageType` | `licensed` (default), `metered` |
| `SubscriptionStatus` | `active` (default), `past_due`, `unpaid`, `canceled`, `incomplete`, `incomplete_expired`, `trialing`, `paused` |
| `UsageEventStatus` | `pending` (default), `reported`, `failed` |

Deleting a tenant cascades to its products, prices, customers,
subscriptions and usage events. A price referenced by a subscription is
set to null when the price is deleted. `Customer.is_deleted` is true when
`deleted_at` is set. A partial index `ix_usage_events_pending` speeds up the
lookup of pending usage events.

## Migrations

The Alembic configuration lives in `apps/billing/alembic.ini` and
`apps/billing/alembic/`. `env.py` reads `DATABASE_URL` and converts the
asyncpg URL to a synchronous one (`postgresql+asyncpg://user@/db?host=...`
becomes `postgresql:///db?host=...`) so that peer authentication over a Unix
socket works; the `sqlalchemy.url` of `alembic.ini` is always overridden.

| Revision | Purpose |
|----------|---------|
| `001` | Create all tables, enums and indexes |
| `002` | Empty revision. It used to seed a fixed tenant; tenants and plans are deployment data created through the API, never by a migration |
| `003` | Add `customers.deleted_at` |
| `004` | Drop the unused `rate_limit_*` columns of `saas_apps` |
| `005` | Add `billing_products.slug` (backfilled from `extra_data.slug` or the product name, duplicates of one tenant get a numeric suffix) with a unique constraint per tenant, add `usage_events.saas_app_id` (backfilled through the subscription) and make the idempotency key unique per tenant, add `saas_apps.checkout_url_allowlist` |

Downgrading `005` restores the global uniqueness of the idempotency key and
fails if two tenants used the same key in the meantime.

```bash
docker compose -f apps/billing/compose.yml up -d    # PostgreSQL on 5435, Redis on 6382
export DATABASE_URL=postgresql+asyncpg://billing:billing@localhost:5435/billing_test
uv run --package billing alembic -c apps/billing/alembic.ini upgrade head
uv run --package billing alembic -c apps/billing/alembic.ini current
uv run --package billing alembic -c apps/billing/alembic.ini revision --autogenerate -m "description"
```

`compose.yml` only starts local PostgreSQL 16 and Redis 7 containers for
development.

## How it is tested

pytest (`apps/billing/tests`):

- `test_models.py`: `Customer.is_deleted`, the enumeration values, the
  per-tenant uniqueness of plan slugs and idempotency keys and the currency
  default read from the settings;
- `test_migrations.py`: the history is linear with the single head `005`,
  and the offline SQL rendering of `upgrade head` creates every table, the
  `deleted_at` column, the revision `005` columns and constraints and seeds
  nothing (no database needed). The backfill statements of `005` are only
  rendered, not executed: they have not been run against a real PostgreSQL;
- `conftest.py` fills the `status` of usage events created by the mocked
  session.

behave (`apps/billing/features/data_model.feature`), against an in-memory
SQLite database where the PostgreSQL `JSONB` columns are rendered as `JSON`:

- A SaaS application gets default values;
- SaaS application slugs are unique;
- A product holds prices with sensible defaults;
- A customer can be soft deleted;
- Subscriptions start active and usage events start pending;
- Two SaaS applications can reuse a plan slug;
- A plan slug is unique inside a SaaS application;
- Two SaaS applications can reuse an idempotency key;
- An idempotency key is unique inside a SaaS application.
